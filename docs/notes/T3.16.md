# T3.16 Backups and restore test

Date: 2026-09-29 · Requirements: NFR-8 · Agent: ops (main agent)

## What was done
- Every night at 02:00, the CronJob `ticket-backup` writes one dated folder to the backup volume `ticket-backups`:
  - a `pg_dump` of the database, custom format, taken as the owner;
  - a tar of the evidence uploads;
  - a `SHA256SUMS` file.
  Folders older than 14 days are deleted. The dump is taken before the tar, so every attachment row in the dump has its file.
- A restore test (`make cluster-restore-test`) takes a backup now, restores it into the scratch namespace `ticket-restore` and compares the result with the live system: counts, files, checksums and the audit_log grants.
- docs/RESTORE.md is the runbook: what is backed up, how to check last night's run, the monthly restore test and a full in-place restore. The in-place restore uses the helper pod in `deploy/restore/restore-pod.yaml`.
- The runbook's in-place restore was drilled step by step on the local cluster: after ticket 7 and its video were deleted, the restore brought both back.

## Decisions
- One image for backup and restore: the same `postgres:16-alpine` as the database, so `pg_dump` matches the server's major version. It already has tar and sha256sum, so there is no custom image.
- The backup runs as user 65532 (the app's user) with `umask 077`. It can read the upload files (0640), and only that user can read the backup files (0600).
- The uploads tar is not compressed: most of its bytes are photos and videos, which are already compressed.
- Redis is not backed up. It holds only sessions, rate-limit counters and live-update messages, so after a restore staff simply sign in again. Vault is also left out here (see Follow-ups).
- Schedule 02:00 in the controller's time zone (UTC on k3s), 14 days kept. Change `schedule`, `spec.timeZone` or `BACKUP_KEEP_DAYS` in backup.yaml.
- Locally the backup volume is local-path on the same disk, as a stand-in for NFS. For the test, the scratch namespace reads the same folder through a static read-only volume, as a pod on the host would mount the NFS share.
  - First try: stream the 126 MB tar through two `kubectl exec` pipes. It failed once with "tar: short read".
  - Now no backup data passes through kubectl.
- The backups are not encrypted. Instead, the NFS share must be exported only to the node's IP with `root_squash`; this is documented in backup.yaml and RESTORE.md. Encrypting them needs a key-custody decision (see Follow-ups).

## Checks
- Test first: `make cluster-restore-test` before the CronJob existed failed with `cronjobs.batch "ticket-backup" not found`.
- `make cluster-restore-test` passes all checks, on the backup set written with `umask 077` (all three files `-rw-------` 65532):
  - checksums ok;
  - tickets, attachments, comments and last audit id `7 6 0 193` equal the live database;
  - every attachment file present with its recorded size;
  - evidence checksum `e00ed782766f48c8` equals the live uploads;
  - `ticket_app` on audit_log: INSERT true, UPDATE false, DELETE false.
  The first run, before `umask 077`, gave the same results. The scratch namespace and its volume are removed afterwards, and earlier backup sets survive.
- Retention: a planted folder dated 2026-09-01 was deleted by the next backup run; the 4 folders from that day were kept.
- In-place drill on `ticket-local`, following docs/RESTORE.md steps 1–9:
  - before: `7 6 0 192`, evidence sum `e00ed782766f48c8`;
  - after deleting ticket 7 and its folder: `6 5 0 192`, sum `6f5da974a3cec636`;
  - after `pg_restore --clean --if-exists --exit-on-error` and the tar: `7 6 0 192`, sum `e00ed782766f48c8`;
  - through the ingress: `/healthz` 200, staff login 200, ticket 7's video downloaded (200, 20971532 bytes, video/mp4);
  - Argo CD automatic sync back on, application Synced Healthy.
- `make deploy-lint`: kube-linter "No lint errors found!" for staging and prod (now including the CronJob); Trivy config clean.
- `/check`: `go vet`, `go test -cover ./...`, golangci-lint "0 issues", `check-i18n` exit 0, svelte-check 0 errors.
- Security review (backup.yaml, restore-pod.yaml, restore-test.sh, RESTORE.md): 1 medium, 2 low.
  - Low, fixed: `umask 077` in the backup.
  - Low, fixed: a deny-all NetworkPolicy for the trust-auth scratch database.
  - Medium, partly fixed: the backups are unencrypted on NFS. The export lock-down is documented; encryption is open under Follow-ups.
  - The reviewer found no problem with password handling, the retention `find` or the audit_log grants after a restore.

## Follow-ups
- Human decision: encrypt the backups, for example with `age` and a key kept in Vault plus an offline copy? A lost key makes every backup useless, so who holds the recovery copy must be decided first. Until then the NFS export must be locked down.
- T3.09 host:
  - point `ticket-backups` at the NFS share, never the node's disk;
  - export the share only to the node's IP, with `root_squash`;
  - run the restore test there once, then monthly.
- Vault: back up its Raft data (`vault operator raft snapshot save`) on the same schedule. Without Vault, a restored cluster has no secrets.
- Alerting: nothing alerts yet when a backup Job fails. Add it with monitoring (a failed Job or no success in 26 hours).
