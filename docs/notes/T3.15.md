# T3.15 CI pipeline, part 2

Date: 2026-09-30 · Requirements: NFR-10 (and NFR-7 for the Vault login) · Agent: ops (main agent)

## What was done
- A merge to `main` now reaches the local cluster, which stands in for staging, with no manual step. .github/workflows/cd-local.yml runs after CI on a GitHub self-hosted runner on the PC that hosts the k3d cluster (label `ticket-local`, `make cluster-runner`). `deploy/local/cd-local.sh` then:
  1. builds the app, migration and backup images;
  2. Trivy-scans each;
  3. pushes it to the local Harbor;
  4. makes a Syft SBOM;
  5. signs the image and attests the SBOM with Vault transit key `cosign` (cosign v2, so Kyverno checks it);
  6. pins the digests in `deploy/overlays/local`.
  Argo CD syncs those digests to `ticket-local` and Kyverno admits the signed images. Last, a ZAP baseline scan of the deployed app runs (`deploy/local/zap-baseline.sh`) and fails the run on a high-risk alert.
- No secret for this is stored in GitHub. The job's own GitHub OIDC token (audience `vault`) logs in to Vault JWT auth `jwt-github`, role `ci`.
  - The role is bound to this repository, `refs/heads/main`, `.github/workflows/cd-local.yml` and a self-hosted runner.
  - It may sign and verify with the Cosign key and read the Harbor robot's login, for 15 minutes; the token is revoked at the end.
- The GHCR pipeline (cd.yml, GitHub's runners, keyless signing, staging digests) stays as it was. The two are separate workflows, so a PC that is switched off only delays the local one.

## Decisions
- Self-hosted runner on this PC: the user's choice on 2026-09-29. GitHub's own runners cannot reach the local Harbor or Vault.
  - The runner runs as the signed-in Windows user, not as a service (no admin rights needed), and stops at sign-out: run `make cluster-runner` again to start it.
  - It can use Docker, so the repository must stay private with trusted collaborators; any workflow that names the label runs on this PC.
- Crane, cosign and vault run in the k3d node's network namespace, like push-images.sh (T3.12). That reaches Harbor and Vault's ClusterIP without exposing Vault on the ingress and without giving CI a kubeconfig.
- Digests go into `deploy/overlays/local` in Git (GitOps). Argo CD keeps `ticket-local` on the CD images: images pushed by `make cluster-images` (tag `local`) no longer deploy unless the overlay points back to them. Session d6 checked that its policy checks do not depend on the tag.
- The ZAP step waits a fixed 150 s for Argo CD and the rollout (`ponytail:` note). In this run the new pods were up after about 2.5 minutes.
- On the T3.09 host, the same job would run on a runner inside the company network, against the real Harbor and Vault, pinning `deploy/overlays/staging`.
