# T2.13 Guest rate limit

Date: 2026-09-24 · Requirements: NFR-3 · Agent: be + fe

## What was done
- `POST /api/tickets` counts every request per client IP in Redis before it reads the body. The 6th request within 10 minutes gets 429 `{"error":"ticket.rate_limited"}` and no ticket is created. The window starts at the first request (INCR + EXPIRE NX in one pipeline), so parallel requests cannot slip through.
- If Redis is down, the endpoint fails closed with 500 `internal` rather than accepting unlimited tickets.
- The limit is 5 by default. The new optional env var `GUEST_TICKET_LIMIT` changes it; a value that is not a positive integer stops the server at startup.
- On a 429, the guest form (/report) shows "You sent several reports in a short time. Please wait 10 minutes, then try again." and keeps what the guest typed. Other API errors now say "Something went wrong" instead of blaming the network.

## Decisions
- Every request counts, including invalid ones. The form validates on the client first, and counting before parsing is simplest and hardest to abuse. Reverse: move the check after `validate()`.
- The counter uses the sessions' Redis client (`s.Sessions.Redis`), the only client the app has.
- The limit is an env var so tests and e2e can raise it. Production keeps the default by leaving it unset.
