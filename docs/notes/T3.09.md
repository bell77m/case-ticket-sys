# T3.09 Cluster host

Date: 2026-10-07 · Requirements: none in PLAN (the host for NFR-1, NFR-4, NFR-7, NFR-8, NFR-10) · Agent: ops (main agent)

## What was done
- One script, `deploy/install/install.sh`, turns a fresh Ubuntu Server 26.04 into the whole platform in one run: k3s without Traefik, ufw, F5 NGINX Ingress, Vault with VSO, Harbor, Kyverno with the four policies, Argo CD, then the app through Argo CD, the first Root Admin and the nightly app and Vault backups. The local k3d cluster proved this same design in T3.10–T3.17.
- The installer builds the three images from the checked-out commit and copies the third-party images, which are pinned by digest. It pushes all of them to Harbor and signs each with the Vault transit key. The app then runs only those images, by digest.
- Every step checks what is already there first. A run that stopped can simply be started again, and a cut-off Helm release is cleared or rolled back.
- Secrets are made on the server and kept in Vault. Only three root-only files hold any: the unseal keys, the offline copy of the backup key and the summary. The summary lists the steps people must still do by hand (docs/INSTALL.md).
- `deploy/install/test-in-docker.sh` tries the installer on a PC. It runs in a privileged Ubuntu 26.04 container with systemd, and the app answers on https://127.0.0.1:9443.

## Decisions
- The user chose the target (Ubuntu Server 26.04 rather than the plan's 24.04), the full platform on k3s, and company CA files with a self-signed fallback. PLAN.md now says 26.04.
- The node runs k3s with `--secrets-encryption` and `--write-kubeconfig-mode=600`, which the plan did not ask for. The k3s binary, Helm and cosign are checked against their published SHA-256, and k3s's install script against a hash kept in the installer.
- Firewall (ufw): 80 and 443 only from `ALLOW_CIDRS`. 6443 stays closed unless `ADMIN_CIDRS` is given (the plan says "6443 admins"; kubectl on the server itself always works). SSH is allowed from `SSH_CIDRS` (default `ALLOW_CIDRS`) and from the SSH session running the installer, so that session is never cut off. Pod and service networks are allowed inside the node.
- The installation's own CA is name-constrained: it can sign only the app and Harbor names, Vault's in-cluster names and 127.0.0.1. The host trusts it, so a stolen CA key cannot be used for other sites.
- On prod, the installer's first sync counts as the manual sync. After that, prod syncs only when an approver presses Sync. On staging, sync is automatic.
- Third-party images are pulled by their pinned digest, but the app runs the digest Harbor holds for the pushed copy. That can be just the amd64 manifest of the pinned multi-platform index, so the content still comes from the pinned image.
- Argo CD deploys the overlay from Git (`REVISION`, default `main`). It patches in this server's names, networks, image digests and backup storage class, so no server-specific file is committed.
- `--small` (no Harbor scanner, Kyverno admission controller only) exists for the 7 GiB Docker VM of the PC test only.
- Harbor's robot accounts never expire. To rotate one, delete its entry in /etc/ticket-install/harbor-robots.json and run the installer again (accepted review finding).
- ClamAV (another session's work, not yet committed when this was written) is not in the committed installer's image list. Add `clamav/clamav:1.5_base@sha256:…` to `THIRD_PARTY` when that work lands.

- Problems the test runs found, each fixed and committed:
  - A slow Docker Hub pull passed harbor-registry's 10-minute progress deadline, and Helm 4 failed at once. Each chart now gets one more try (`chart()`).
  - The k3s restart for registries.yaml restarts Harbor too, and `docker login` got 502. The installer now waits for Harbor's health to report `healthy`.
  - curl's `--retry` does not retry an SSL read error mid-file, and `fetch a && fetch b` turned that into a false "checksum mismatch". Now `--retry-all-errors`, and `fetch` fails with the URL.
  - The review's `docker logout` ran before `cosign sign`, which pushes signatures with Docker's login, so every signature failed. The logout now runs after signing.
  - Docker 29.8.2 (Docker Desktop updated itself during the test) pushed only the amd64 manifest of a multi-platform image, yet reported the index digest. Harbor never had that digest, so Kyverno refused the pods. The digests now come from Harbor's API for the pushed tag.
  - A rerun now stops a first sync left unfinished by the run before.
- Reruns after a failure at steps 3, 7, 8 and 12, and after the container was stopped, all resumed and finished. That proves the "run it again" path.
- `shellcheck` (koalaman/shellcheck:stable): clean for install.sh and test-in-docker.sh. The k3s install script at v1.35.5+k3s1 hashes to the pinned `8598e002…`.
- Security review of install.sh: 7 medium and 9 low findings, all fixed except one low (Harbor robots never expire; accepted, rotation documented). The fixes: the pinned k3s script and image digests, the name-constrained CA, secrets passed to jq through its environment (checked with a jq run), the root-only `--config`, input validation, 6443 closed by default, the SSH rule for the installing session, the root-admin.out cleanup step, the logout, the sync JSON built with jq, and the /etc/hosts note.
