# T3.11 Vault

Date: 2026-09-28 · Requirements: NFR-7 (and NFR-1 for the TLS certificate) · Agent: ops (main agent)

## What was done
- HashiCorp Vault 2.0.4 runs in the cluster (Helm chart 0.34.1, values `deploy/platform/vault-values.yaml`):
  - one Raft node (3 for HA);
  - a TLS listener using Secret `vault-tls`;
  - a file audit device on its own volume;
  - the agent injector off.
  It is initialised with 5 key shares, 3 needed to unseal.
- The Vault Secrets Operator 1.6.0 (`deploy/platform/vso-values.yaml`) connects over HTTPS with CA Secret `vault-ca`. From `deploy/base/vault.yaml` it creates:
  - `ticket-app-secrets` (the six keys the app, the migration Job, PostgreSQL and Redis read);
  - `ticket-app-tls` (the Ingress certificate).
  Both come from `secret/ticket/<env>/app` and `secret/ticket/<env>/tls`, re-read every 60 s. A changed value restarts the app and Redis.
- Access is least privilege: policy and role `ticket-<env>` can only read that environment's entries, bound to ServiceAccount `ticket-app-vault` in that namespace, audience `vault`, 1 h tokens. The ServiceAccount token is never mounted in a pod.
- The local overlay no longer generates Secrets. `deploy/local/vault-setup.sh` (`make cluster-vault`) does these, safe to rerun:
  - initialises or unseals Vault;
  - turns on auditing first;
  - enables KV v2 and Kubernetes auth;
  - writes the policy and role;
  - loads the random local values from the gitignored files.
  So the local cluster runs the same secret path as staging and prod.

## Decisions
- Proven on the local k3s cluster (user's choice, 2026-09-28). Still to do on the T3.09 host:
  - the real unseal ceremony: five people each get one key, and the root token is revoked after setup;
  - Vault's own certificate from the company CA, created as `vault-tls`/`vault-ca` before install (Vault cannot serve its own certificate);
  - the staging and prod values written into `secret/ticket/staging|prod/*`;
  - the same policy and role commands as the script, with `env` set to staging or prod.
- Locally the unseal keys and root token sit in the gitignored `deploy/local/vault-init.json`. That is acceptable only on a throwaway laptop cluster.
- KV v2 static secrets (not dynamic database credentials): the app and Redis read passwords from environment variables at start, and PostgreSQL only at first init. Rotating a database password is a manual step: `ALTER ROLE` in PostgreSQL, then the new value in Vault.
- `rolloutRestartTargets`: the app Deployment and the Redis StatefulSet (Redis reads `REDIS_PASSWORD`). PostgreSQL is left out, because restarting it would not apply a new password.
- VaultAuth audience `vault` and 1 h role tokens (VSO renews them).

## Checks
- `make cluster-vault`: initialised, unsealed with 3 of 5 keys sent on stdin, audit device on, "Vault ready: sealed=false". After Vault moved to TLS: `VAULT_ADDR=https://127.0.0.1:8200`, unsealed again by the same script.
- `kubectl get vaultstaticsecret,vaultauth`: both secrets SYNCED/HEALTHY/READY True; VaultAuth True. VaultConnection `default`: `https://vault.vault.svc.cluster.local:8200`, CA `vault-ca`, valid true.
- `ticket-app-secrets` (Opaque) and `ticket-app-tls` (kubernetes.io/tls) are owned by their VaultStaticSecret and labelled `managed-by: hashicorp-vso`. The migration Job completed; both app pods are Ready.
- `make cluster-check-ingress`: 12/12 PASS with the Vault-delivered certificate and secrets.
- Rotation: a new key written to `secret/ticket/local/app` reached the Kubernetes Secret after about 15–35 s; the app rolled to a new ReplicaSet and `redis-0` was replaced. The entry was then reset to the local values.
- Audit log: 100 lines after the first run, including VSO's `auth/kubernetes/login` requests.
- Nothing secret in Git:
  - Gitleaks git mode: 12 commits, "no leaks found".
  - Gitleaks dir mode finds only gitignored local files (`vault-init.json`, `deploy/overlays/local/secrets.env` and `tls/`, the inlang cache).
  - `git ls-files` lists none of them.
- `make deploy-lint`: kube-linter "No lint errors found!" for staging and prod; Trivy config clean.
- Security review (vault.yaml, both values files, vault-setup.sh): 3 medium and 2 low, all fixed:
  - token and unseal keys moved from command arguments to stdin;
  - `vault-init.json` can no longer be emptied: temp file, `umask 077`, refusal to re-init, stop on status errors;
  - audit enabled before other changes;
  - TLS for Vault and VSO in the shared values files;
  - Redis added to the restart targets.
  The policy, role, ServiceAccount and placeholders checked out.
