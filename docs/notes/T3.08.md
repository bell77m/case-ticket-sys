# T3.08 Burmese and Thai input

Date: 2026-09-27 · Requirements: FR-I8, FR-I9 · Agent: fe

## What was done
- Burmese typed in the Zawgyi encoding is converted to Unicode in the browser before it is sent. This covers the guest form, guest replies, staff comments, admin names and every other JSON write, because they all go through `call()` in `frontend/src/lib/api.ts`.
- `call()` loads the converter only when a request body contains Myanmar script. It then converts each string value that myanmar-tools rates as Zawgyi with probability above 0.95. Unicode Burmese, Thai and English are sent as typed.
- Fields whose name contains password, token, secret or code are never touched.
- The converter is a separate 54 KB chunk (`toUnicode` in `frontend/src/lib/zawgyi.ts`), loaded with a dynamic `import()` only on the first Burmese submit.
- FR-I9 was already met: the Noto fonts are bundled through Fontsource. The visual check below confirmed that no page loads anything from outside the app.

## Files
- frontend/src/lib/zawgyi.ts (new): builds the myanmar-tools detector and converter and exports `toUnicode`.
- frontend/src/lib/api.ts: `call()` passes JSON bodies that contain Burmese through `toUnicode`, skipping secret-named fields.
- frontend/e2e/tracking-page.spec.ts: new test `Zawgyi input is saved as Unicode`.
- frontend/vite.config.ts: `optimizeDeps.include: ['myanmar-tools']`. Without it, the dev server finds the lazily imported package on the first Burmese submit and reloads the page mid-submit.
- frontend/package.json, frontend/package-lock.json: `myanmar-tools` pinned to exactly `1.1.3`.

## Decisions
- **Where conversion runs.** It runs in the browser, in the one shared request function, not in each form or in the Go API. To reverse, call `toUnicode` from individual forms, or convert on the server instead.
- **Threshold.** A string is converted only when its Zawgyi probability is above 0.95, so Unicode text is never altered by mistake. myanmar-tools documents no threshold. On the test sample, Zawgyi scored 1.0 and Unicode 0.0. To change it, edit the constant in zawgyi.ts.
- **Skipped fields.** The skip is by field name, matching `/password|token|secret|code/i`; it came from a low finding in the security review. To change it, edit that regex in `call()`.
- **Version pin.** myanmar-tools is pinned to 1.1.3 because 1.2.0 on npm has no `build_node/` folder and fails to load. With `^1.1.3`, npm would install 1.2.0.
- **Buffer workaround.** The npm package contains only the Node build, which decodes its model with Node's `Buffer`. zawgyi.ts sets a small browser `Buffer` on `globalThis` only while constructing the detector, then deletes it. Remove this if a future version ships a browser build.
- **Queue search.** The search box sends a GET query, not a submit, so it is not converted (FR-I8 says "before submit").

## Follow-ups
- Text sent to the API without the SPA (curl, a future integration) is not converted. The server does not detect Zawgyi.
- A Zawgyi search in the queue will not match Unicode tickets. Convert the `q` parameter too if staff need it.
- The `my` and `th` UI strings are still mostly English placeholders, so the visual check covered layout and user content, not translated labels. Repeat the check after T3.07.
- Tickets already saved as Zawgyi stay as they are; there is no data migration. In the dev DB, #2766 comes from the test run before the fix.
- qrcode and chart.js are not in `optimizeDeps.include` either, so the first dev run after a config change reloads open pages once.
