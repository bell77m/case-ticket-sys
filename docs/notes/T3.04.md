# T3.04 Realtime updates

Date: 2026-09-27 · Requirements: FR-P3, NFR-9, FR-R3 · Agent: be + fe

## What was done
- When any ticket changes (guest creates, uploads, replies or confirms; staff change status, priority, category, assignee or comment; auto-close), the API publishes `{"type":"ticket","id":N}` to Redis channel `ticket-events` after the commit. Events carry no ticket content.
- `GET /api/events` (staff with ticket.view_all) streams those events as server-sent events from whichever pod the browser is connected to. Every 25 s it sends a `: ping` and re-runs the same session and permission check as `require`; deactivation, a password change or reset, or a removed permission ends the stream.
- The staff queue, the reports dashboard and the ticket detail page refetch when an event arrives (bursts coalesce into at most one refresh per 300 ms). On the detail page, unsaved form edits are never overwritten: a notice with "Reload form" appears if they clash, and Save sends only the user's own changes.
- After a dropped stream reconnects (pod restart, proxy timeout), the browser sends every page a catch-up refresh, so changes made during the gap are not missed.

## Decisions
- One Redis subscription per SSE client (marked `ponytail:` in events.go). Fine for tens of staff; switch to one subscription per pod fanned out to local clients if staff grow into the hundreds.
- `/api/events` needs ticket.view_all (every default role has it); the dashboard's report.view is checked by its own endpoint when it refetches.
- The API needed no new Redis field or main.go change: handlers use the sessions' client.
- Detail page: the read-only parts always refresh; form edits stay, with a "Reload form" notice on conflict, and Save sends only changed fields.
- Catch-up after reconnect is a synthetic event with id 0 (built in the browser, not sent by the server).
