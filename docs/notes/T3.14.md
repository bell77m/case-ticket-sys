# T3.14 Argo CD and GitOps repo

Date: 2026-09-28 · Requirements: none (deploy task; release flow in docs/ARCHITECTURE.md) · Agent: ops (main agent)

## What was done
- Argo CD v3.5.3 (Helm chart argo/argo-cd 10.9.2, values `deploy/platform/argocd-values.yaml`) deploys the app by pulling the Kustomize overlays from Git every 60 s. CI never holds cluster credentials.
- Application `ticket-staging` syncs `main` by itself (prune, self-heal), so the digests cd.yml commits reach staging without a manual step. Application `ticket-prod` syncs only when an admin presses Sync.
- Two AppProjects limit what the Applications may touch:
  - `ticket-staging` may deploy only to `ticket-staging` and `ticket-local`;
  - `ticket-prod` only to `ticket-prod`, and its always-open deny sync window blocks every automatic sync there while still allowing a manual one.
  Both accept only this repo, Namespace at cluster scope and the namespaced kinds deploy/base uses.
- Argo CD reads the repo through a read-only GitHub deploy key; the private key sits only in Secret `repo-ticket` in the `argocd` namespace.
- `make cluster-argocd` installs all of this on the local k3d cluster, with Application `ticket-local` for the local overlay.

## Decisions
- The GitOps source is this repo's `deploy/overlays`, not a separate GitOps repo (same interim choice as cd.yml). To move later: point `sourceRepos` and each Application's `repoURL` at the new repo and give Argo CD a deploy key there.
- Read-only deploy key (user's choice, 2026-09-28) rather than a GitHub App or token. Revoke it on the repo's Deploy keys page; `make cluster-argocd` registers a new one when the gitignored key file is missing.
- One AppProject per environment (security review), so the staging project can never target prod even if an Application is edited. Prod's manual gate is also enforced by the project's deny window, not only by `prod.yaml` lacking `automated`.
- The projects list the allowed namespaced kinds. Secret, Role and RoleBinding are not in them, so a commit to `main` (the CD bot can push there) cannot plant credentials or grant permissions. A new kind in deploy/base must be added to both lists, or the sync fails.
- Secrets that hold keys are applied with `kubectl apply --server-side`, so no copy of the key lands in the `last-applied-configuration` annotation. This also changed for `vault-tls` and `vault-ca`; the annotation was removed from the three Secrets already in the local cluster.
- Prod follows `main` too, but syncs only by hand: the release tag is set in deploy/overlays/prod by a pull request, then an admin presses Sync.
- Dex and notifications are off: admins use the built-in `admin` account (port-forward only, no Ingress) until named accounts are set up (see Follow-ups).

## Checks
- `make cluster-argocd`: Argo CD installed; deploy key added on GitHub; `ticket-local` "Synced Healthy", sync "successfully synced (all tasks run)".
- Zero downtime (the done criterion), on the local cluster through the ingress:
  - Setup: Application `ticket-local` pointed at a throwaway branch, `argocd-rollout-test`. A commit there changed the image tag from `local` to `local2`.
  - Measure: `/healthz` polled about every 0.75 s during the whole rollout.
  - Argo CD saw the commit and changed the image after 106 s (60 s polling), ran the migration Job hook and rolled both pods. Result: 198 requests, 198 × 200.
  - Moving the Application back to `main` rolled back to `local` (image changed after 23 s): 48 requests, 48 × 200.
  - The test branch and its worktree were then deleted.
- Every kind in the local overlay synced under the kind allow list: Job hook, VaultAuth, VaultStaticSecrets, Policy, Ingresses and the rest all "Synced".
- Project limits, tested with two throwaway Applications, deleted afterwards (no finalizers, so nothing cascaded):
  - an automated Application in `ticket-prod` stayed "OutOfSync Missing" with no sync operation, and namespace `ticket-prod` was never created;
  - an Application in `ticket-staging` aimed at `ticket-prod` got "InvalidSpecError: … do not match any of the allowed destinations in project 'ticket-staging'".
- `kubectl apply --dry-run=server` of both projects and the staging and prod Applications: accepted. `kubectl kustomize` of both overlays renders only kinds in the allow lists.
- `make deploy-lint`: kube-linter "No lint errors found!" for staging and prod; Trivy config clean.
- `/check`:
  - `go vet`, `go test -cover ./...`, golangci-lint "0 issues", svelte-check 0 errors, `check-i18n` exit 0;
  - the frontend has no `lint` or `test` npm scripts, so those were skipped.
- Secrets: `git check-ignore` covers both key files; `git ls-files deploy/local` lists none.
- Security review (values, projects, Applications, Makefile): 2 medium.
  - Staging and prod shared one project, so an edited staging Application could have auto-synced prod. Fixed: split projects plus the deny window, and the test above.
  - Only the shared `admin` account can approve prod syncs, with no per-person audit. Left open: see Follow-ups.
  - Inline review before that (the agent call was blocked for a while): the `last-applied-configuration` copy of the private keys. Fixed.
